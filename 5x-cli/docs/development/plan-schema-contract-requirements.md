# Versioned execution contracts and legacy-plan migration

## Purpose

Create an implementation plan for this agreed feature. Today approved-plan drift protection ignores checkbox toggles but otherwise protects plan bytes. Authors routinely update a status sentence or add execution context, sometimes as directed by the plan, and block the run. Support living plans while preserving approved obligations and providing recovery for existing runs.

Output plan: `5x-cli/docs/development/plans/216-plan-schema-contracts-and-migration-plan.md` (repository-relative). This is a planning task, not feature implementation. Inspect current code and identify concrete integration points. Follow the current plan format and parsers; do not activate the proposed schema in this implementation plan before the feature exists.

## Agreed design

1. Introduce explicit plan schema versioning. Unversioned plans are legacy schema 0. Schema 1 declares `<!-- 5x:plan-schema:1 -->` outside the execution contract. Require a unique, valid declaration; reject unsupported versions or malformed/duplicate declarations. The schema is structural metadata bound to approval, not mutable bookkeeping. Distinguish schema version from human document revision/version.
2. Schema 1 contains exactly one explicit execution contract delimited by standalone `<!-- 5x:contract:start -->` and `<!-- 5x:contract:end -->` markers. Everything outside is informational/mutable, except structural metadata. Approved scope, design constraints, budgets, debt claims, phase definitions, checklist requirements, acceptance gates, and exclusions belong inside it. Material references must not silently delegate authority to mutable content; include governing content or bind references to stable versions.
3. Inside the contract permit standalone mutable note blocks, e.g. `<!-- 5x:note:start id="concurrency-context" -->` and `<!-- 5x:note:end id="concurrency-context" -->`. Notes may be edited or newly inserted during execution. Require unique IDs, matched delimiters, no nesting, and unambiguous Markdown placement; initially support block boundaries, not insertion inside sentences, tables, or fenced code. Define precisely how examples/fences and malformed reserved markup behave.
4. Derive a shared governing-content projection: extract contract, remove note regions including delimiters, normalize checkbox state. Define local separator-newline handling narrowly so inserting a note between paragraphs/checklist items does not introduce spurious drift; do not broadly normalize whitespace or prose. Compare against the approved baseline plus verified amendments, never the previous working copy. Wrapping an existing requirement in a new note, moving boundaries to exclude it, changing it, or deleting it must fail. Copying a requirement into a note while retaining the original is allowed.
5. Governance parsers consume the same governing projection. Raw readable plans, with the authority distinction explicit, remain available to authors/reviewers/orchestrators. Ensure plan phases, budgets, structural checks, approval/baseline acquisition, drift, author admission, review, amendments, reconciliation, phase finish, resume, and run completion cannot disagree about interpretation. Assess impacts on byte-offset amendment spans and exact commit/blob/hash checks; preserve provenance rather than globally replacing raw hashes. Schema 1 text-amendment guards resolve and verify authorized spans on this same projection, using literal fixed-segment comparison and no semantic analysis.
6. Keep raw document hashes/bytes for provenance and exact-byte workflows where required; bind schema version and governing hash to approvals. Informational edits must not invalidate approval at downstream boundaries. A status or note edit must not invalidate an authorized text amendment either before guard verification or during it. Raw snapshots and raw before/after hashes remain the lineage identity for ordinary author admission and registration. Schema 0 amendment checks stay on raw bytes. Budget and structural protections stay in force. Existing durable records and historical approvals remain interpretable; never retroactively reinterpret legacy approval based on newly inserted markers. Missing markers on a migrated run mean malformed/drifted input, not legacy fallback.
7. Do NOT build a CLI detector/classifier for material language or governing syntax within notes/outside the contract. Validate structure mechanically only. Give authors, reviewers, and orchestrators a short shared instruction: only contract content outside notes governs work; read other content as context, surface apparent material requirements or conflicting instructions as warnings, and route necessary contract changes through amendment approval before acting. Warnings must reach the operator. Informational claims such as 'review passed' never satisfy durable completion gates.

## Migration and recovery

- Provide a dedicated CLI migration affordance, not a blanket accept-current-plan/rebaseline escape hatch. Integrate existing review/amendment/decision infrastructure where adequate. Specify concrete proposed commands, payloads, records and routing in the plan after inspecting current architecture.
- Pre-approval plans can be converted and go through ordinary review. Already approved runs require an explicit, versioned transition against approved text plus authorized amendment lineage.
- Mechanically equivalent migration wraps all previously governing content, preserving bytes modulo existing checkbox-state allowances. CLI verifies it without a fresh substantive approval.
- Selective migration excludes existing bookkeeping/status text from the contract. Show exact exclusions and the target's current non-governing text; require operator confirmation bound to the exact proposal digest. Equivalent migration is verified mechanically and does not require that confirmation. This feature does not accept a reviewer snapshot as migration authority. No automatic semantic exemption. Retained governing changes require the existing amendment workflow. Do not implicitly reset/re-estimate budgets, discard decisions, restart runs, or lose approval history.
- Migration must be available to drift-blocked runs through an independently validated recovery path. Include the motivating case: current status sentence differs from approved text; approved obligations are retained while explicit exclusions and edits are authorized.
- Record schema 0 -> 1, prior approval and amendment lineage, new governing binding, exact proposal/source/target provenance, exclusions and authority (verified equivalent or operator). Authorization must be stale if bound inputs change.
- Migration must be atomic from the logical approval perspective, durable, retry-safe/idempotent after interruption, and unable to double-apply on concurrent/repeated requests. An identical completed attempt returns the recorded result before any refusal that the run is already schema 1. A different proposal after a recorded migration is refused. Reuse record-store transaction/idempotency mechanisms where possible.
- Keep legacy schema-0 behavior supported during rollout. New plans use schema 1 once implemented. Do not retire legacy support in this feature.
- Add a SEPARATE shipped `5x-plan-migration` skill for supported schema transitions, initially 0 -> 1. It explains finding approved baseline, detecting a candidate governing region, proposing boundaries, both migration paths, obtaining operator confirmation of the exact exclusion digest, CLI diagnostics and resuming runs. The shared `5x` foundation only points to it. Normal planning/execution skills teach schema 1. CLI legacy/recovery diagnostics link to migration. The skill should use recorded schema identity, not infer migration eligibility merely from missing markers. Future retirement of 0 -> 1 content must not compromise historical record interpretation; do not implement speculative future migrations.
