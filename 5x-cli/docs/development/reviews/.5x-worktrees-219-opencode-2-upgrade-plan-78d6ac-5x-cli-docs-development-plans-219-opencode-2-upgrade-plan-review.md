## High Priority (P1)

### R7 — Tie settlement to delivery of the submitted prompt

**Classification:** acceptance_required; auto_fix. **Budget evidence:** effortDelta 2; architectureDelta 0; high confidence; reviewer verification required.

**Risk:** On a resumed session with a previous turn still active (including external OpenCode activity), the previous turn's terminal SSE event can end the new invoke while its prompt is still pending. The invocation can read no reply or the wrong reply, attribute the previous turn's usage, or start the summary prematurely.

**Requirement / evidence / correction:** Turn-loop steps 3–5 distinguish admission from completion in prose, but the streaming predicate is still “first terminal event for this session.” In V2, `session.prompt` returns an inbox item, `session.inbox.delivered` identifies delivery by `inboxID`, and terminal events have only session identity, not prompt identity. Keep same-session filtering, but establish ownership of the turn before accepting its events or usage: reject an already-active or pending session when ownership cannot be established, observe delivery of the exact inbox item (or the corresponding durable evidence), and do not return success on an ambiguous overlap. Specify this consistently for streamed and polled settlement, retaining the early-failure path after delivery from historical R3. Add a scripted test with the previous same-session terminal event before this prompt's delivery.

### R8 — Cancel pending work as well as running work

**Classification:** acceptance_required; auto_fix. **Budget evidence:** effortDelta 2; architectureDelta 0; high confidence; reviewer verification required.

**Risk:** An external invocation reports timeout or cancellation while its prompt is queued and subsequently runs. An unconditional session interrupt can stop a different execution rather than removing the cancelled request.

**Requirement / evidence / correction:** Design failure handling and Phase 2.3 specify only `session.interrupt`; the edge-case list names cancellation before admission but gives it no semantics. V2 `session.interrupt` stops a running agent, not a pending inbox item. V2 2.4.2 accepts a caller-assigned prompt `id`, and `session.inbox.cancel` removes an undelivered item. Short-circuit pre-aborted turns; keep a stable request ID across an in-flight admission whose response may be lost; bound the admission, poll and cleanup requests; cancel the owned pending item or interrupt the owned active execution. Specify handling of cancellation racing delivery and test both cancellation with a delayed/lost acknowledgment and cancellation of a known queued item. Preserve the typed timeout/cancellation behavior without relying on a terminal event after the local signal aborts.

### R9 — Route headless forms by their actual session discriminator

**Classification:** acceptance_required; auto_fix. **Budget evidence:** effortDelta 1; architectureDelta 0; high confidence.

**Risk:** In the explicitly planned fallback if question denial does not suppress forms, the provider drops its own `form.created` event and the unattended invocation stalls.

**Requirement / evidence / correction:** The general filter in Design step 4 and Phase 2.5 only reads `data.sessionID`. V2 `form.created` contains `data.form`, with `sessionID` and `id` inside that object. Specify the event-specific extraction and pass the form ID to cancellation. Exercise a matching form and a foreign-session form in the fallback; make the live deny-or-cancel exercise explicit in §2.6, rather than treating a successful normal text/tool turn as denying a question.

### R10 — Use an executable Phase 1 unit-test gate

**Classification:** acceptance_required; auto_fix. **Budget evidence:** effortDelta 0; architectureDelta 0; high confidence.

**Risk:** The literal completion command exits nonzero on the known Phase 1 tree even when there are zero test failures; a clean execution cannot use the result as proof of passing that command.

**Requirement / evidence / correction:** The Phase 1 gate says `bun test test/unit` must pass. The Phase 1 review at `ce74d860` reports that exact command exited 1 on both base and implementation, while `bun test --concurrent --parallel=2 --dots --timeout 15000 test/unit` exited 0 on the implementation. Use the known passing configured unit invocation in the gate. This is not a checkbox repair and does not redo Phase 1 or waive any required execution evidence.

### R11 — Pipe managed stderr explicitly

**Classification:** acceptance_required; auto_fix. **Budget evidence:** effortDelta 0; architectureDelta 0; high confidence.

**Risk:** A managed process that exits before listening cannot provide the bounded stderr tail required for its startup error; it can also emit diagnostics directly to the caller's stderr instead of the managed capture.

**Requirement / evidence / correction:** The literal spawn in Design specifies only stdin and env for descriptors. A Bun probe confirmed stderr is inherited by default. Specify `stdout: "pipe"` and `stderr: "pipe"` and have the existing spawn-seam test assert those options, in addition to argv and env. No new process facility is necessary.

### R12 — Exercise real reviewer output through `5x invoke`

**Classification:** acceptance_required; auto_fix. **Budget evidence:** effortDelta 1; architectureDelta 0; high confidence.

**Risk:** AC1 can be signed off without a single reviewer invocation passing role-specific CLI validation over the new transport. The native installed delegation exercise does not exercise the invoke provider, and an author-shaped object is not a ReviewerVerdict.

**Requirement / evidence / correction:** §2.6's live schema is author-shaped and §5.2 steps 4–5 invoke only the author. The handler in `src/commands/invoke.handler.ts` requires a run and validates against the invoked role. Seed a valid temp-project plan/run and select the bundled provider explicitly, keep both author smokes, and run one unrecorded reviewer invocation through the same CLI fixture in each mode. Verify accepted ReviewerVerdict output (including the rendered review context's required fields), not just successful JSON parsing.

### R13 — Require positive live evidence for the advertised minimum

**Classification:** acceptance_required; auto_fix. **Budget evidence:** effortDelta 1; architectureDelta 0; high confidence.

**Risk:** The live gate can exit successfully with both tests skipped when explicitly requested, or advertise 2.4.0 even though only 2.4.2 ran. This can certify unsupported installations.

**Requirement / evidence / correction:** Design calls 2.4.0 the oldest verified version, but the prototype says 2.4.2, and §2.6 skips even when explicitly enabled if the local binary does not qualify. The Phase 2 checklist says to set the minimum to the oldest verified version, but the gate accepts a run merely at or above it. Skip only when opt-in is absent; fail clearly on bad prerequisites when opted in, and record successful managed/authenticated external cases on the advertised minimum or raise the constant to the oldest release actually verified. Apply the same rule to final verification and make the provider's old-2.x diagnostic name the minimum and use the doctor check's ordinary upgrade hint.
