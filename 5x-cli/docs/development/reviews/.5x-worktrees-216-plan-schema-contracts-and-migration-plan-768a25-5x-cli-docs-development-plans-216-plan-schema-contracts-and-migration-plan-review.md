## Summary

The plan is grounded in the code. Almost every cited line and symbol exists as described: `detectPlanDrift`, `replayTextAmendments`, `normalizeCheckboxMarkers`, `listImplementationTextAmendments`, `appendPlanReviewPromptContext` with native and invoke parity, `BASE_SKILL_TEMPLATES`, the bind path, and recover-plan's `atomicAppendIfAllNew` use. The layering is sound: recorded schema wins over the file, raw hashes stay raw, migration is a lineage record, and there is no prose classifier.

One core path stays broken on schema 1. Text-amendment guards are anchored to the raw authorized lineage, and `verifyGuardedPlanBytes` compares raw bytes outside the spans. Once an author makes any informational edit that schema 1 allows, every later text amendment and every guarded author admission fails with `PLAN_AMENDMENT_OUT_OF_SPAN`. That contradicts requirement 6. The reviewer-authority migration path also cannot be reached as specified, and a few mechanical gaps could corrupt the lineage or misplace spans.

**Readiness:** Not ready. Two items need a design decision (P0.1 and P1.3). The rest are mechanical.

## Strengths

- **Recorded schema beats file contents.** Expected schema comes from the binding or a replayed migration and never from a missing marker. A schema 1 file with missing markers fails as `PLAN_SCHEMA_INVALID`. This closes the main reinterpretation hole for historical approvals.
- **Additive record evolution.** The binding gets optional fields with no version bump and no SQLite migration. Unknown budget kinds are already skipped (`review-budget-store.ts` 472–495, `sqlite-index.ts` 255–259). Old binaries fail closed. I traced bind, recover-plan, and drift on an older CLI, and each refuses rather than mis-authorizing.
- **The migration reuses the recover-plan pattern.** It uses one `atomicAppendIfAllNew` batch with an idempotency key that carries the digest. It never sets `completionAuthorized`, and it never resets the baseline.
- **One shared projection with two views.** The offset-preserving mask is used for parsing and spans, and `comparisonBytes` is used for hashing. `hashPlanBytes` stays the only hash implementation.
- **Asset coverage follows AGENTS.md.** The plan covers the skeleton, all nine templates, the runtime append for stale overrides, the harness `listBaseSkillNames()` iteration, and the focused acceptance suite.

## Production readiness blockers

### P0.1 — Text amendments are unusable on schema 1 once any informational edit exists

**Risk:** `implementation-review-context.ts:531–556` snapshots the text guard against `anchor.authorizedBytes`, which is the raw replayed lineage and not the worktree. `implementation.ts:911–928` resolves spans against those same bytes. `verifyGuardedPlanBytes` (`plan-amendment.ts` 352–414) then checks `fixedSegmentsMatch(normalize(anchor), normalize(committed), spans)` on raw bytes. Suppose the author changed the status line or added a note, which is the main purpose of schema 1. The committed blob then differs from the anchor outside the authorized spans, and verification returns `PLAN_AMENDMENT_OUT_OF_SPAN`. This happens on every guarded author step: `admitAuthorTextAmendment` runs before the `unchanged` check, so even a step with no span edit is blocked. Re-snapshotting does not help, because the anchor is always lineage bytes, which never contain informational edits. The plan's Design Decision ("Guard verification continues to compare raw buffers … A note inserted after a guard snapshot makes that guard stale") covers only the after-snapshot case. It misses the general case, and in practice the code returns `OUT_OF_SPAN`, not `STALE`. Requirement 6 says "Informational edits must not invalidate approval at downstream boundaries," and the plan's scope lists amendments as a governing-projection consumer.

**Requirement:** On a schema 1 run, a text amendment whose committed blob differs from the authorized lineage only in (a) the authorized spans, (b) checkbox state, and (c) non-governing lines (outside the contract, or note blocks and their delimiters) is verified. The recorded `authorizedPlanBytes` are the committed raw blob, and the before and after raw hashes are kept. A governing byte change outside the spans still fails. Schema 0 behavior is unchanged.

**Implementation guidance:** This needs a decision. Options:

- (a) Run the fixed-segment check over a projection: compare the governing comparison projection of the anchor with spans applied against the projection of the committed blob, mapping spans through the line-aligned mask.
- (b) Accept raw differences only on lines that are non-governing in both the anchor and the committed document, using line-aligned diffing outside spans.
- (c) Keep raw verification and require authors to commit amendments on top of the exact lineage bytes, then re-apply informational edits. Templates and skills would have to say this. It meets the letter of the requirement poorly.

Whichever option is chosen, add `plan-amendment.test.ts` and `implementation-state.test.ts` fixtures: a status edit followed by a span amendment that verifies, a note followed by a span amendment that verifies, and a governing edit outside the span that still fails. Apply the same schema 1 projection to the `unchanged` check at `implementation-state.ts` 1430–1434.

## High priority (P1)

### P1.1 — The `authorityMarkdown` offset contract contradicts itself

Design Decisions says non-governing lines are blanked "in place … so character offsets in the raw file stay valid." The `LoadedPlanDocument` doc comment says "every other line empty. Same line count as raw." Empty lines keep the line count but shift every later character offset. Span resolution (`resolvePlanImpactSpans` with `section.lineStart + hit`) and guard ranges would then point at the wrong raw bytes. There is a second trap. `protectedPlanByteRanges` (`plan-markdown.ts` 151–158) converts character ranges to bytes with `Buffer.byteLength(markdown.slice(...))`. Called on the mask, it gives wrong byte offsets whenever a blanked line contained non-ASCII text.

**Fix:** Blank by replacing each non-newline UTF-16 code unit with a space, keeping `\r` and `\n`. State that char-to-byte conversion always slices the raw string using the mask's character ranges. Add a fixture with a non-ASCII status line above a governing span.

### P1.2 — recover-plan's earlier-phase equality is still raw on schema 1

`implementation-recovery.ts` around lines 299–320 compares each earlier phase's raw line slice, checkbox-normalized and trimmed, between the authorized lineage and the committed plan. The plan converts lines 266, 327, and 329 to the mask but does not mention this comparison. A note added in a completed earlier phase is allowed and does not drift, yet it would make every later `recover-plan` reject with "Earlier phase … changed". Running the comparison on the mask would not help either, because blanked note lines still add lines.

**Fix:** On schema 1, compare each earlier phase section's governing comparison projection (note lines removed, splice rule applied). Add this site to §2.2's call-site list and add a recover-plan fixture with a note in an earlier phase.

### P1.3 — The reviewer-authority migration path cannot be reached

§3.3 requires the `--snapshot` to "belong to this run," to have "a completed plan review" route, and to have a review-commit plan blob exactly equal to `--commit`. Neither eligible run type can supply that:

- A bound execution run records implementation reviews, not plan reviews.
- An approved source plan-review run is already `completed`. Its snapshots reviewed the pre-migration commit, so they can never equal the migrated `--commit`.

Nothing defines a focused review of the exclusion manifest either: no template, no prompt context that carries the exclusions, and no route. The requirements ask for "explicit focused reviewer approval *or* operator confirmation."

**Decision needed:** One choice is to define how a focused reviewer approval is produced. That means deciding which run it lives on, how the exclusions and digest reach the reviewer, and which verdict or route counts. The other choice is to drop reviewer authority from this feature, ship operator confirmation only, and keep the `"reviewer"` enum value reserved. Update §3.3, the tests, and the migration skill to match.

### P1.4 — A sequential second migration permanently poisons the lineage

The command accepts any bound execution run or any approved, unbound source run. It does not require the run's expected schema to still be 0. Replay rejects `fromSchema` other than 0 and rejects "a second migration in one chain." The idempotency key includes the digest. A second invocation therefore appends cleanly if it comes after the first one commits, with fresh `expectedKeys` and a different target or digest, or if it targets a schema 1 binding created from a source migration. The chain then becomes invalid, and because records are append-only, admission is drift-blocked with no recovery. The same problem applies to two source-run migrations, where bind's "one valid source-run migration" lookup becomes ambiguous.

**Fix:** Before dry-run or write, refuse with `PLAN_MIGRATION_CONFLICT` in three cases: the binding has `planSchema: 1`, the replayed lineage already contains a valid migration, or the source run already has a migration record. The identical-digest retry still returns the stored winner. Add tests for a second migration with a different target and for a migration on a schema 1 binding.

### P1.5 — Exclusion `currentText` and the diff alignment are undefined

The payload and dry-run both depend on per-exclusion `currentText`. The motivating case ("dry-run shows the approved status text, the current status text") pairs a removed governing line with a line that is now outside the contract. The plan never says how that counterpart is found, and the digest hashes it. The line-diff algorithm is also unspecified. With repeated lines such as blanks, `---`, or table separators, different LCS alignments produce different exclusion lists and different digests.

**Fix:** Name a deterministic line diff over governing lines, for example Myers or LCS with earliest-match tie-breaking, and define exclusion ids from approved line numbers. Replace the per-exclusion `currentText` pairing with one recorded `nonGoverningText` block: the target's non-governing lines with their line numbers, hashed into the digest. Dry-run shows that block as the current text. This satisfies "show exact exclusions and current changes to excluded text" without a semantic pairing heuristic.

## Nonblocking follow-ups

- The proposal digest does not bind `runId`, `bindingId`, or `mode`. A confirmation printed for a source run could be pasted onto an execution run that shares the same approved bytes and a null parent. Since it authorizes the same exclusion, this is harmless, but binding `runId` is cheap.
- The `schema-migration` step's `phase` and `iteration` values are unspecified. Phase 0 should confirm that a non-reviewer step appended after `run:complete` on a completed source run leaves `terminalRoute`, `resolveFinalizedPlanCommit`, and `foldGoverningReviewState` unchanged.
- For source-run migration, the requirement that "the worktree plan blob must equal that commit" is ambiguous once the plan-review worktree is gone. Name which worktree is checked, or check only the commit blob in that mode.
- `5x plan phases` uses file mode even on a bound schema 1 run whose markers were deleted, so it would display schema 0 phases. It is display only, but it should probably use the expected schema when a binding exists.
- Equivalent migration keeps `**Status:**` inside the contract, so status edits still drift afterward. The migration skill should say that selective mode is the path for the motivating status-line case.

### What's addressed (✅)
- **P0.1 — schema 1 guard verification:** Addressed. Guards resolve spans on the space-filled mask and verify with literal fixed segments on the governing projection. The unchanged check is projected too. Raw anchors, raw `authorizedPlanBytes`, and raw before/after hashes stay the lineage identity, and `PLAN_AMENDMENT_STALE` is limited to raw lineage mismatches. Budget-table and structural protections stay in force. Fixtures cover status-then-amendment, note-then-amendment, status-only unchanged, and governing edits outside the span.

- **P1.2 — recover-plan earlier phases:** Addressed. Schema 1 compares each earlier phase's `governingLines`, with a fixture and a Files Touched row.
- **P1.3 — reviewer authority:** Addressed by removing it. Selective migration is operator digest only, with no `--snapshot` flag and no reviewer authority value or snapshot id. The requirements say reviewer approval *or* operator confirmation, so this is within scope. Equivalent mode stays a mechanical proof.
- **P1.4 — second migration:** Addressed. An identical completed retry returns the stored record first. Otherwise a schema 1 binding, an existing lineage migration, or an existing source-run migration is `PLAN_MIGRATION_CONFLICT` before any append. The replay chain also rejects a second migration.
- **P1.5 — exclusion diff:** Addressed. Earliest-match LCS defines one alignment, and ids come from approved line numbers. One hashed `nonGoverningText` block replaces per-exclusion pairing, and the digest binds `runId`.
- **P2.1 — decisions in `expectedKeys`:** Addressed in Design Decisions, §3.3, and the tests.

The Delivery Budget rows now carry `Addresses` values for these IDs. None of the findings remains open, so no `Addresses` value points at an open item.
