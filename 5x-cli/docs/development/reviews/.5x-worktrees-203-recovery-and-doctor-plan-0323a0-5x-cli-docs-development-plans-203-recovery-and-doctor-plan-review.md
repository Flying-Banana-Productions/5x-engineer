# Review: Recovery & `5x doctor` plan

**Review type:** `docs/development/plans/203-recovery-and-doctor-plan.md`  
**Scope:** Recovery commands, remediation, step budgets, doctor checks/fixes.  
**Reviewer:** Staff engineer (reliability, operability)  
**Local verification:** Static review; inspected referenced design and implementation.

## Summary

The plan is well phased, preserves additive output compatibility, and anchors most work in existing seams. It is not ready because the proposed DB inspection path can mutate/migrate the database, and doctor repairs do not preserve the established freshness safety predicate. The corrupt-lock repair also has no usable target once its plan path is unreadable.

**Readiness:** Not ready — three correctness gaps must be resolved.

---

## Strengths

- Clear completion gates and unit/integration split.
- Lock operations retain existing ownership semantics and force is explicit.
- Step-budget behavior specifies threshold, idempotency, output modes, and boundaries.
- Doctor correctly limits destructive fixes and separates warning from failure semantics.
- Reuses the 201 freshness seam rather than duplicating fingerprint logic.

## Production readiness blockers

### P0.1 — DB doctor inspection must not open through a migrating/creating context

**Action:** `auto_fix`

**Risk:** `resolveDbContext()` migrates by default and `getDb()` creates the parent/file and sets WAL. Using either for doctor makes a supposedly report-only DB check mutate a missing/outdated database and prevents it from reliably reporting an old schema. This contradicts the plan's “never migrates” guarantee.

**Requirement:** Specify a non-mutating DB-resolution path: derive the same control-plane DB path, do not create a missing DB, open an existing DB read-only (without migration/WAL setup), and turn open/query/integrity failures into DB findings. Define missing-DB status explicitly.

**Implementation guidance:** `src/commands/context.ts:82-149` and `src/db/connection.ts:16-67` show why the existing helpers cannot be used unchanged; build an inspection helper or add a read-only/no-migrate variant.

---

### P0.2 — Doctor harness `--fix` must retain the 201 lossless-refresh predicate

**Action:** `auto_fix`

**Risk:** The plan permits sync for any project-scope stale finding “without a hand-edit” gate. But `harnessSyncCore()` only blocks modified assets; it force-installs even when `installedFrom.contextDir` differs. That overwrites root assets baked for another monorepo context, violating 201 D6.

**Requirement:** Gate doctor auto-sync on both the matching install context and unchanged recorded asset hashes. Context-mismatched project installs remain fail/warn with remediation, without writes. Re-run/check the result and record `fixed` only after a verified successful repair.

**Implementation guidance:** Align Phase 5.1 with `docs/v2/201-harness-freshness.md:171-175`; `src/commands/harness.handler.ts:742-844` demonstrates that sync itself does not apply the context guard.

---

### P0.3 — Corrupt locks need a safe addressable removal path

**Action:** `auto_fix`

**Risk:** A corrupt entry has no `plan_path`; `unlock <plan>` cannot find it because `findExistingLock()` skips unparsable noncanonical files. Consequently neither the advertised unlock remediation nor doctor `--fix` can remove an arbitrary corrupt lock, despite both claiming to do so.

**Requirement:** Define an internal, lock-directory-confined operation that revalidates the selected entry is corrupt and removes that exact `lockPath`; use it for doctor. Give `lock list` output/remediation an executable safe path for corrupt entries, or deliberately limit the CLI command and state doctor-only handling.

**Implementation guidance:** `src/lock.ts:65-88, 192-227` establish the lookup limitation; `LockEntry.lockPath` is available for a constrained helper.

## High priority (P1)

### P1.1 — Isolate individual doctor-check failures into findings

**Action:** `auto_fix`

A corrupt/unopenable DB, inaccessible worktree, or failed freshness plugin load must produce a `fail` finding and allow independent checks to run. Specify per-check exception conversion and a stable diagnostic code; otherwise `doctor` itself crashes precisely when needed most.

### P1.2 — Make `--fix` report mechanics concrete

**Action:** `auto_fix`

`DoctorCheck.run(ctx)` returns only findings, while `DoctorReport.fixed` has no producer and the plan says “re-status” without defining replacement/removal of repaired findings. Add a check result/fix contract (or handler algorithm) that records successful repairs and reruns detection before calculating `report.ok` and exit code.
