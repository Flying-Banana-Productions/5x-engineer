The proposed durable extensions fit the existing immutable binding, effective-plan lineage, Git evidence, and paired RecordStore boundaries.

## Strengths

- **Repair authority is explicit and proactive.** The run form works during drift and without an existing gate; native chat authorization is recorded once, and unchanged repair intent survives preview refresh.
- **Mechanical proof is narrow.** Requirement wording, nesting, order, phase identity, schema, and budget/debt contracts stay fixed. New checkboxes start unchecked, including normalization of manually introduced checked markers.
- **Work preservation is an acceptance condition.** Unchanged review, quality, due-claim, and completed-phase evidence remains usable; unrelated findings are not resolved by formatting. Newly introduced boxes still require matching obligations to evidence.
- **Approval provenance is separated from reviewer history.** A finalization anchor reconciles final committed bytes and ledger without rewriting the original snapshot or relaxing exact-hash assessment of semantic amendments.
- **Tests measure operator experience as well as record correctness.** Same-run recovery, invocation counts, restart/replay, historical inconsistent state, and effective installed/override-rendered assets are required outcomes.

## Source and design cross-checks

- `src/parsers/plan.ts` recognizes checklist/subheading forms and counts top-level list items; it currently allows COMPLETE headings to affect display and does not filter fenced examples itself. The shared parser/validation changes and zero-item COMPLETE regression are therefore necessary and correctly specified.
- `src/plan-schema/authority.ts` supplies the expected-schema authority reader used by the proposed shared result. Plan 216's governing projection and raw-hash distinction are preserved; checklist repair does not silently perform schema migration.
- `src/review-governance/implementation-state.ts:246–344` compares normalized existing checkbox state but still detects marker introduction as drift. Its source approval selection at `1084–1100` takes the finalized commit while retaining the review snapshot ledger, and `1234–1251` admits the recorded final-correction author route. These seams support the plan's diagnosis and separate repair/finalization design.
- `src/review-governance/routing.ts` retains the bounded initial-plan final-correction policy and amendment reassessment distinction. The plan explicitly reuses that policy rather than adding universal re-review.
- `src/review-governance/implementation.ts:525–539`, `src/commands/implementation-review-context.ts:721–729,868–899`, and `src/review-governance/store.ts:568–572` explain how negative readiness can yield a human route without a gate cause. Composition, persistence, and readback all need the planned invariant; changing only display would be insufficient.
- `src/review-governance/code-diff.ts:879–934` already distinguishes ordinary implementation defects from structural plan findings. `src/templates/reviewer-commit-continued.md:56–65` states the hunk rule too broadly. The plan correctly treats this as context/instruction repair and anchored evidence validation, not a need for a duplicate finding class.
- `src/commands/plan-v1.handler.ts:463–477` emits `data.phases[].id`, confirming the planned correction of skill completion queries.
- The author generation prompt already requires per-phase checklist items. The configured repository skeleton is weaker; updating both configured and bundled surfaces is appropriate.
- Existing schema-migration/RecordStore seams already demonstrate source-versus-binding subject selection, paired records, replayable lineage, and captured stream preconditions. Reuse is appropriate; no additional persistence service, independent gate database, or new lock system is needed by this design.
