### R1 — Make discovery validate source artifacts and inspect existing linked PRs

**Action:** `auto_fix`  
**Plan locations:** Design Decisions, source markers/discovery (lines 60–68); Phase 1.1; Phase 3 Step 0.

The specified discovery only searches the new 5x PR-body marker. It does not actually obtain the existing issue-linked PRs required by requirements §4 before choosing new work. An existing human-created, unmarked PR can therefore be missed and a duplicate resolution started. The intake snapshot is named `linked-prs.json`, but its retrieval is not concretely specified either.

The proposed unrestricted regex `git grep -l` is also not a source-identity check. The dots in `github.com` are regex wildcards, and it searches arbitrary files, including the intentionally preserved untrusted issue/comment JSON. A pasted or hostile marker in source text can create a false candidate. A grep hit alone does not identify a brief's first-line marker or its associated plan.

**Lowest-cost correction:** Define ordinary `gh` queries for issue-linked PRs as well as marker/branch matches, and preserve their results in the intake snapshot. Use literal candidate search followed by exact first-line marker, canonical repository/issue, and associated-plan validation on recognized brief artifacts at the searched ref. Specify how a validated brief's source files are pinned to their original Git commit/blob for later comparison; supply that committed brief/snapshot reference to issue-aware reviewers rather than relying on an unversioned live path. Preserve historical snapshots on incomplete-intake continuation. Do not introduce a new index or package store.

**Acceptance evidence:** Add fixtures for an unmarked linked PR, a marker quoted inside raw issue/comments JSON, a mismatched source identity, and discovery from a remote branch without the original chat. Mark agent-driven discovery as manual unless a real command seam is exercised.

**Failure prevented:** Duplicate implementation or incorrect source/plan association, including treating untrusted snapshot text as workflow identity.

**Budget evidence:** `acceptance_required`; effort delta 1; architecture delta 0; confidence high. This tightens the already planned discovery/provenance assets and fixtures.

### R2 — Reconcile refresh, sealed-run immutability, and expected closure transitions

**Action:** `auto_fix`  
**Plan locations:** Snapshot refresh rule (line 58), delivery protocol (line 99), Resume algorithm step 5 (line 109), reconciliation rule 7 (line 111), Phase 3 Steps 4–5.

The refresh rule universally creates a new source JSON and brief addendum, while delivery refresh/resume can happen after both runs have sealed and the plan forbids post-merge Git receipts. The orchestrator is also explicitly unable to author these files. There is no viable writer/run specified for that refresh path.

Separately, step 5 treats any state change from the intake snapshot as material and stops before reconciliation. After this workflow successfully closes an initially open issue, every later resume sees that exact state change and stops. It also prevents the explicitly promised externally-closed reconciliation branch from running. Reopened-after-closure cannot be recognized merely by comparing an initially open snapshot to a currently open issue.

**Lowest-cost correction:** Separate read-only remote refresh from persisted pre-seal source revisions. Persist pre-seal revisions only through a bounded author in the appropriate active run; after sealing, use read-only comparison and GitHub receipts, with no brief/journal edits. Order the reconciliation checks so the workflow's own marked closure and externally closed issues have explicit branches; detect reopening against a prior delivery/closure receipt, not just original intake state. Keep material body/comment/acceptance changes fail-closed and route them to clarification/amendment without automatically reopening a sealed run.

**Acceptance evidence:** Include unchanged second resume after successful close, externally closed before delivery reconciliation, reopening after a marked close, material new comments, and read-only post-seal refresh in the command/fixture/manual matrix.

**Failure prevented:** Normal retries become permanently blocked; expected closure is mistaken for scope drift; or the workflow violates its no-post-seal-write boundary.

**Budget evidence:** `acceptance_required`; effort delta 1; architecture delta 0; confidence high.

### R3 — Specify authoritative delivery endpoints and recognize normal governed completion

**Action:** `auto_fix`  
**Plan locations:** Reconciliation rule 2 (line 111), PR handoff (line 113), Phase 3.2 final bullet (line 295).

The fallback conflates `final_head_commit` and a review-document commit with a reviewed implementation endpoint. Current `run-v1.handler.ts:4502–4537` records the checkout head before the sealing commit; it is not proof of the review range. `reviewer-commit.md:22` explicitly forbids substituting a review-document commit for runtime endpoints. The source already exposes `.data.implementation_governance.reviewedRange.{baseCommit,reviewedCommit}` (`run-v1.handler.ts:1235–1241,1458–1467`), but that is the latest observation's range, not necessarily the whole multi-phase delivery range or a later quality-backed final correction.

The comparison rule then permits only active-run records after that reviewed head. Normal workflow commits also write review documents and plan checkboxes, and an admitted final-correction route can legitimately change code with recorded quality proof. Consequently a normal successfully completed implementation can be rejected as changed reviewed code. Conversely, an endpoint-only `git diff --name-only A..B` does not establish that B descends from A or that every intervening commit is records-only; divergent equal trees or a code change followed by reversion can pass that stated test.

**Lowest-cost correction:** Resolve the exact accepted code endpoint and its provenance from durable implementation contexts, observations, completion/correction evidence, and the sealed run. Distinguish latest review range, overall delivery range, and final sealed branch head. Use the runtime range when bound; limit legacy document/step extraction explicitly to the unbound compatibility path and stop if it cannot establish exact endpoints. Check ancestry and the stated per-commit/path allowance using the configured workflow-evidence paths, allowing normal review/checklist/seal commits and CLI-authorized quality-backed corrections without pretending they were part of an earlier review. Continue to verify squash delivery through the PR head, not merge parentage. Compare PR-body claims back to committed run evidence rather than trusting mutable body text alone.

**Acceptance evidence:** Deterministic Git/protocol fixtures for normal review-document and checkbox commits, records-only seal commits, approved final correction, unauthorized code changes, divergent heads, multiple implementation phases, absent governance in compatibility mode, and squash merge. Existing executable Git/governance helpers can test identity properties; a prose assertion is not behavioral coverage. No new workflow engine is required.

**Failure prevented:** False delivery attestation from an untrusted endpoint, or blocking valid ordinary completion and squash delivery.

**Budget evidence:** `acceptance_required`; effort delta 2; architecture delta 0; confidence high; reviewer verification required. This completes an explicitly unresolved source-verification seam in the current plan, without changing the governance API.

### R4 — Keep plan-review and implementation-review classifications separate in every mode

**Action:** `auto_fix`  
**Plan locations:** Reviewers verify coverage (line 86); Phase 2.2–2.3 (lines 203–209).

The design says both reviewer types use `acceptance_required` for missing criteria, contradicting Phase 2.3 and the existing implementation finding domain. Phase 2.3 also states implementation-only finding classes unconditionally. Existing `reviewer-commit.md:72` explicitly keeps mode-off and unbound runs on the v1 contract and omits implementation-only fields. Adding an unconditional issue-specific classification rule would conflict with that compatibility instruction.

**Lowest-cost correction:** State consistently that plan review uses plan-budget classes only when applicable; bound implementation review uses `implementation_defect` with approved W IDs for work inside the approved obligation and `plan_defect` when correction requires changed approved scope. Preserve source-of-correction precedence and all existing hunk/plan-impact requirements. Explicitly defer to v1 output in off/unbound compatibility mode. Apply the same wording to initial/continued variants.

**Acceptance evidence:** Render/classification contract assertions for plan versus bound implementation versus off/unbound contexts. Tests should ensure the new clause cannot override the existing domain rules.

**Failure prevented:** An otherwise valid issue-acceptance finding is rejected or routed through the wrong review/amendment domain.

**Budget evidence:** `acceptance_required`; effort delta 0; architecture delta 0; confidence high. This is a contradictory sentence/qualification correction within W2, not new implementation scope.

### R5 — Complete the publication and synchronization failure branches

**Action:** `auto_fix`  
**Plan locations:** Delivery protocol and outcome vocabulary (lines 99–101); reconciliation rules 5–6 (line 111); Phase 3 Steps 4–5 and Formats.

The detailed steps assume push/PR authorization and advance from comment publication to closing the issue without defining failure exits. The only concrete `delivered_sync_pending` condition in the reconciliation rules is a pending release restriction. Requirements §6 also mandates that merged delivery followed by failed comment/close returns synchronization-pending with actionable resume steps, and that absent publication authorization produces a concrete publication handoff. These are known required paths, not optional hardening.

**Lowest-cost correction:** Add explicit no-authorization and failed-push/PR publication handoffs without implying a PR exists. After merge, require successful or re-read-confirmed marked evidence publication before attempting close. Failed or unknown comment/close operations must return `delivered_sync_pending` with the exact missing operation and resume instruction; re-read first on retry and reuse the marked comment/PR. Do not report `resolved` until acceptance, delivery conditions, published evidence, and final closed state are all verified. Ensure the externally-closed path does not publish a misleading success claim before its checks.

**Acceptance evidence:** Add comment-create timeout, comment-update failure, close timeout after successful comment, denied publication authorization, and failed push cases to the matrix/formats. Distinguish executable gh-stub contract checks from manual agent rehearsal.

**Failure prevented:** Premature issue closure, false success after a failed remote write, duplicate comments on retry, or an unusable handoff when publication is not authorized.

**Budget evidence:** `acceptance_required`; effort delta 1; architecture delta 0; confidence high.
