## High priority (P1)

### P1.1 — `--fix` re-detect matching keyed on `code` alone under-reports `report.fixed`

**Action:** `auto_fix`

The normative handler algorithm in Phase 4.2 decides "finding cleared" via `again.some((f) => f.code === candidate.code && f.status === "fail")`. When two findings share a code — the common case is two stale locks, both `LOCK_STALE` — fixing lock A re-detects lock B's still-present `LOCK_STALE` and withholds A's `fixed` entry; after fixing B, only one `fixed` entry is recorded even though two repairs succeeded. Exit code and the final findings list stay correct, so this is reporting-only, but the algorithm is presented as normative and an implementer following it verbatim ships an inaccurate `fixed` report (and the text formatter's `Fixed:` section undercounts).

**Recommendation:** Match on identity, not code: compare `code` plus the finding's identifying detail (`detail.lockPath` for `LOCK_CORRUPT`, `info.planPath`/plan path for `LOCK_STALE`, `harness`+`scope` for freshness, `planPath` for worktree mappings). A small `findingKey(f)` helper in `src/doctor/registry.ts` used by both the handler loop and tests is enough. Also note that the candidate loop iterates the original `detected` array after `current = again`; this is safe only because every specified `fix` helper re-validates its target (`removeCorruptLock` re-reads, `releaseLock` handles `not_locked`) — state that invariant as a requirement on `DoctorCheck.fix` so future checks preserve it. Add a unit test: two stale locks, `--fix` → both removed, `report.fixed.length === 2`.

## Addendum (2026-08-18) — v1.4 re-review

**Reviewed:** `3e0e0ff` | plan v1.4 (diffed against `8f8e019`, the v1.3 revision this review's prior addendum covered)

### What's addressed (✅)

- **P2.4 — `findingKey` empty-identity guard for future fixable codes (addressed, and more robust than requested).** `findingKey` (`src/doctor/registry.ts`, Phase 4.1 code block) now throws `Error` when `f.fixable === true` and the computed identity component is `""`, instead of silently returning `${check}:${code}:`. The Phase 4.2 handler wraps both call sites: `findingKey(candidate)` is validated *before* `check.fix` is invoked (so no write is attempted on a malformed candidate — CHECK_FAILED is recorded and the check's remaining candidate loop stops, but `current` — the untouched pre-fix findings — is preserved and still reported), and the post-repair `findingKey` comparison inside the re-detect `.some(...)` is wrapped identically (falling back to the same `current = []` pattern already used for a throwing `check.run()` during re-detect, which is consistent with that pre-existing precedent, not a new pattern). I traced both code paths end to end against the normative Phase 4.2 algorithm; the control flow is sound, `report.ok`/exit code stay correctly derived from `findings` regardless of which branch fires, and the new test-checklist items (Phase 4.1, 4.2, and the Tests table) cover the direct-throw and handler-level cases. This closes the exact gap I raised in the prior addendum: a future fixable code added without a `findingKey` switch case now fails loudly in tests rather than silently reintroducing the P1.1 under-counting bug.
- One design choice introduced by this revision — the pre-fix throw causes `break` (stop this check's *entire* remaining candidate loop) rather than `continue` (skip only the malformed candidate and keep fixing the rest) — is explicit and intentional per the prose ("stop this check's candidate loop — other checks still run"), not an oversight. I consider this a defensible fail-safe choice (treat an identity-computation bug as reason to stop touching that check for this run) and am not raising it as an issue.

### New issue found in this revision

**P2.5 — `findingKey`'s empty-identity throw guard does not fire for the two-field harness identity when both fields are missing.**

- **Action:** `auto_fix`
- **Where:** Phase 4.1 code block, `src/doctor/registry.ts` `findingKey`, the `HARNESS_STALE` / `HARNESS_UNKNOWN` case:
  ```typescript
  case "HARNESS_STALE":
  case "HARNESS_UNKNOWN":
    return `${String(d.harness ?? "")}:${String(d.scope ?? "")}`;
  ```
- **Failure scenario:** The invariant this revision adds is "throw when `fixable` and `ident === ""`." For the three single-field identity codes (`LOCK_CORRUPT`, `LOCK_STALE`/`LOCK_LIVE`, `WORKTREE_MAPPING_MISSING`), a missing identifying detail correctly collapses `ident` to `""` and the throw fires. For the harness case, the identity is built by string-concatenating two fields with a fixed `:` separator. When *both* `detail.harness` and `detail.scope` are absent (or when the finding's `detail` isn't an object at all — `d` becomes `{}`), the expression evaluates to `${String(undefined ?? "")}:${String(undefined ?? "")}` = `":"` — a one-character string, not `""`. I verified this directly: `ident = ":"`, and `ident === ""` is `false`, so a `fixable: true` `HARNESS_STALE`/`HARNESS_UNKNOWN` finding with no `harness`/`scope` detail silently produces the key `harness-freshness:HARNESS_STALE::` instead of throwing — exactly the silent-collapse failure mode this whole hardening pass exists to prevent, for the one identity shape it doesn't cover. (A partial case — `harness` present, `scope` missing — has the same gap: `"opencode:"` is also non-empty and also slips past the guard.)
- **Why it's still P2, not P1/P0:** Phase 5.1 already requires the harness-freshness check to set both `detail.harness` and `detail.scope` on every finding it emits (stated explicitly: "`harness` + `scope` are required — they are the `findingKey` identity for `HARNESS_STALE` / `HARNESS_UNKNOWN`"), so this gap does not manifest in any of the five checks this plan specifies. It's a hole in a defense-in-depth guard against a *future* implementation mistake, in the same speculative category as the original P2.4 — but since the guard's entire stated purpose is "fail loudly instead of silently collapsing," and one of its four covered codes still silently collapses under the qualifying condition, it's worth closing in the same pass rather than carrying it forward again.
- **Recommendation:** Make the two-field case return `""` (not a colon-joined partial string) whenever either sub-field is empty, so the existing `ident === ""` check catches it uniformly with every other code:
  ```typescript
  case "HARNESS_STALE":
  case "HARNESS_UNKNOWN": {
    const harness = String(d.harness ?? "");
    const scope = String(d.scope ?? "");
    return harness && scope ? `${harness}:${scope}` : "";
  }
  ```
  No other call site or test needs to change — the existing throw guard and the existing "two-instance disambiguation" behavior (distinct `harness`/`scope` pairs still produce distinct non-empty keys) are both preserved; only the "both/either field missing" degenerate case now correctly triggers the throw instead of silently keying to `":"` or `"<harness>:"`.
