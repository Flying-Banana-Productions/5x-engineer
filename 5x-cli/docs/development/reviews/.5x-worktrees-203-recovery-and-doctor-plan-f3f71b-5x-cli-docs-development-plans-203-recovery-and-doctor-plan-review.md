## High priority (P1)

### P1.1 — `--fix` re-detect matching keyed on `code` alone under-reports `report.fixed`

**Action:** `auto_fix`

The normative handler algorithm in Phase 4.2 decides "finding cleared" via `again.some((f) => f.code === candidate.code && f.status === "fail")`. When two findings share a code — the common case is two stale locks, both `LOCK_STALE` — fixing lock A re-detects lock B's still-present `LOCK_STALE` and withholds A's `fixed` entry; after fixing B, only one `fixed` entry is recorded even though two repairs succeeded. Exit code and the final findings list stay correct, so this is reporting-only, but the algorithm is presented as normative and an implementer following it verbatim ships an inaccurate `fixed` report (and the text formatter's `Fixed:` section undercounts).

**Recommendation:** Match on identity, not code: compare `code` plus the finding's identifying detail (`detail.lockPath` for `LOCK_CORRUPT`, `info.planPath`/plan path for `LOCK_STALE`, `harness`+`scope` for freshness, `planPath` for worktree mappings). A small `findingKey(f)` helper in `src/doctor/registry.ts` used by both the handler loop and tests is enough. Also note that the candidate loop iterates the original `detected` array after `current = again`; this is safe only because every specified `fix` helper re-validates its target (`removeCorruptLock` re-reads, `releaseLock` handles `not_locked`) — state that invariant as a requirement on `DoctorCheck.fix` so future checks preserve it. Add a unit test: two stale locks, `--fix` → both removed, `report.fixed.length === 2`.
