## High priority (P1)

### P1.1 — `--fix` re-detect matching keyed on `code` alone under-reports `report.fixed`

**Action:** `auto_fix`

The normative handler algorithm in Phase 4.2 decides "finding cleared" via `again.some((f) => f.code === candidate.code && f.status === "fail")`. When two findings share a code — the common case is two stale locks, both `LOCK_STALE` — fixing lock A re-detects lock B's still-present `LOCK_STALE` and withholds A's `fixed` entry; after fixing B, only one `fixed` entry is recorded even though two repairs succeeded. Exit code and the final findings list stay correct, so this is reporting-only, but the algorithm is presented as normative and an implementer following it verbatim ships an inaccurate `fixed` report (and the text formatter's `Fixed:` section undercounts).

**Recommendation:** Match on identity, not code: compare `code` plus the finding's identifying detail (`detail.lockPath` for `LOCK_CORRUPT`, `info.planPath`/plan path for `LOCK_STALE`, `harness`+`scope` for freshness, `planPath` for worktree mappings). A small `findingKey(f)` helper in `src/doctor/registry.ts` used by both the handler loop and tests is enough. Also note that the candidate loop iterates the original `detected` array after `current = again`; this is safe only because every specified `fix` helper re-validates its target (`removeCorruptLock` re-reads, `releaseLock` handles `not_locked`) — state that invariant as a requirement on `DoctorCheck.fix` so future checks preserve it. Add a unit test: two stale locks, `--fix` → both removed, `report.fixed.length === 2`.

## Addendum (2026-08-18) — v1.3 re-review

**Reviewed:** `8f8e019` | plan v1.3 (diffed against `4e9feae`, the v1.0-header revision this review originally covered)

### What's addressed (✅)

- **P1.1 — `--fix` re-detect matching (addressed).** A `findingKey(f)` helper is added to `src/doctor/registry.ts`'s code block: `${check}:${code}:${identity}`, where identity is `detail.lockPath` for `LOCK_CORRUPT`, `detail.planPath` for `LOCK_STALE`/`LOCK_LIVE`/`WORKTREE_MAPPING_MISSING`, and `detail.harness`+`detail.scope` for `HARNESS_STALE`/`HARNESS_UNKNOWN`. The Phase 4.2 handler algorithm now matches "cleared" via `findingKey(f) === findingKey(candidate)` instead of `code` alone. I re-traced the two-stale-locks scenario against the updated algorithm: fixing lock A's re-detect no longer matches lock B (different `planPath` in the key), so `fixed.push` fires for both, giving `report.fixed.length === 2` as required. Phases 5.1–5.3 now require the identifying field on every finding that carries a code the switch handles (including `LOCK_LIVE`, which isn't fixable but gets `detail.planPath` anyway for consistency). I checked every `fixable: true` code emitted anywhere in the plan (`LOCK_STALE`, `LOCK_CORRUPT`, `HARNESS_STALE`, `HARNESS_UNKNOWN`, `WORKTREE_MAPPING_MISSING`) against the `findingKey` switch — all five are covered, so there's no risk of two distinct fixable findings silently colliding on the current check set. New unit test checklist items (Phase 4.1, 4.2, 5.2, Tests table) explicitly cover `findingKey` disambiguation and the two-stale-locks case.
- **P2.1 — Version header (addressed).** Header now reads `**Version:** 1.3`, `**Status:** Ready for implementation`, with a `**Last updated:** August 18, 2026` line added. A new `## Revision History` section (with TOC entry) documents 1.3's changes against this review and points back at 1.2.
- **P2.2 — `DoctorCheckContext.dbPath` type/comment (addressed).** The stale "Null only if path math itself cannot run" sentence is removed; the comment now states `dbPath` is always a resolved path string and that `resolveDoctorContext` fails the whole command if path math cannot run. Phase 4.2 gained an explicit normative sentence to match: control-plane/DB path resolution failures raise a `CliError` rather than producing a context with a missing path, and checks only ever `existsSync` the resolved path.
- **P2.3 — Phase 6.4 / 203 §2.1 reconciliation (addressed).** Phase 6.4's documentation checklist now includes amending 203 §2.1's `isLocked`/`readLockFile` sketch to the implemented `listLocks` scan (with the same corrupt-file rationale from the Design Decisions section), plus an explicit list of six previously-open 203 TODOs to record as resolved (warn → exit 0, doctor + `lock list` both ship, 24h lingering-run age, `--force` + visible holder for PID reuse, fixed 80% step-warning threshold, plugin checks deferred). ### Remaining concerns

- **New, minor (P2, forward-looking, not blocking):** `findingKey`'s `default: return ""` means any *future* fixable code added to a check without a matching case in the switch would silently collapse identity to `${check}:${code}:` for every instance — reintroducing exactly the P1.1 bug for that new code, but silently (no test would fail until someone specifically re-derives the two-instance scenario). This isn't a defect in anything the plan currently specifies — I verified all five fixable codes in the current check set are covered — but nothing enforces the invariant going forward. A cheap hardening option worth considering during Phase 4 implementation: assert in the handler (or in `findingKey` itself, dev-mode only) that a `fixable: true` finding never produces an empty identity component, so a future check that forgets to add itself to the switch fails loudly in tests rather than silently under-reporting `fixed`. Not required to start implementation; flagging as a P2 for the implementer to consider, not a plan defect.
